# Pre-Deployment Security Checklist

> The full pre-production security checklist — kept here so [ROADMAP.md](./ROADMAP.md) stays a lean, current-state tracker. Unlike [planning-history.md](./planning-history.md), this file is *not* frozen: it still has open items and gets updated as they close. For *why* decisions were made, see `docs/adr/`.

Compiled from a full audit (docs/ADRs vs. actual backend/frontend/CI code) on 2026-07-29; re-audited 2026-07-31 against 7 named items (authorization, input validation/sanitization, CORS, password reset link expiration, frontend error handling, logging/alerts in prod, rollback strategy). Several items previously implied as covered turned out to be narrower than they looked, so the still-open list grew from 1 to 6 items. The user has confirmed all remaining items get implemented, not deferred.

## Done

- [x] `gitleaks` CI scanning + custom ruleset for this app's secret shapes, `.github/dependabot.yml` (maven/npm/github-actions) — PR [#53](https://github.com/Efren707/toptrader/pull/53), amends ADR 0007
- [x] Dependency vulnerabilities: `bcprov-jdk18on` → 1.84 (PR [#51](https://github.com/Efren707/toptrader/pull/51)), `fast-uri` → 3.1.4 (PR [#52](https://github.com/Efren707/toptrader/pull/52)), `esbuild`/`@hono/node-server` pinned + `brace-expansion`/`tar` audit-fixed (PR [#54](https://github.com/Efren707/toptrader/pull/54)) — frontend at 0 known vulnerabilities
- [x] Explicit `application-prod.properties` + explicit actuator lockdown — committed prod profile (`spring.profiles.active=prod`) with explicit CORS origin (no unsafe localhost fallback), stack-trace suppression, actuator health-only/no-details, `jpa.show-sql=false`; secrets/DB config stay env-var-only, never committed — see [ADR 0032](./adr/0032-prod-config-shape.md)
- [x] Session timeout/fixation — explicit `.sessionManagement(session -> session.sessionFixation().migrateSession())` in `SecurityConfig.java` (previously implicit default), explicit `server.servlet.session.timeout=30m`
- [x] Frontend 401/403 handling consistency — route-guard coverage was already fine (parent-level `authGuard` covers all protected children, `checkSession()` blocks bootstrap via `provideAppInitializer` so no race on refresh); the real gap was a mid-session 401 (e.g. after the new 30m timeout) going unhandled. New `session-expired.interceptor.ts` clears `currentUser` and redirects to `/login` on any 401 outside `/auth/login`, `/auth/register`, `/auth/session` — manually verified in-browser (session-cookie deletion → redirect; wrong password on `/login` still shows inline, no redirect loop)
- [x] Logging/PII guard — no logging framework exists yet so nothing is at risk today; recorded the binding policy for whenever logging is added (never log full bodies, secret-carrying DTOs must mask `toString()`, log identifiers not object graphs) — see [ADR 0033](./adr/0033-logging-pii-policy.md)
- [x] CSP directives — finalized and empirically verified against the real production build output; required disabling Angular's critical-CSS inlining (`inlineCritical: false` in `frontend/angular.json`) to avoid needing any `'unsafe-inline'`/hash/nonce exceptions — see `docs/architecture/security-architecture.md`
- [x] General API rate limiting — implemented per [ADR 0034](./adr/0034-api-rate-limiting.md): `RateLimitGroup` (matchers/keying/thresholds enum) + `RateLimitFilter` (bucket4j-caffeine, wired into `SecurityConfig`'s filter chain after `CsrfCookieFilter`), `429` + RFC 7807 body + `Retry-After`. Along the way found and fixed a real regression the feature introduced: the filter ran before Spring Security's authorization check, so anonymous/`@WithMockUser` requests hit an unchecked cast in `authenticatedUserId()` and threw `ClassCastException` — all 6 `QuoteControllerTest` tests were failing. Fixed by treating a non-`UserPrincipal` context as "pass through, let the real auth check reject it" instead of crashing. New `RateLimitFilterTest` (3 tests: register threshold + response shape, quote per-user isolation, trade's shared buy/sell bucket) plus the full backend suite (50 tests) verified green after the fix.
- [x] Ticker input validation — `QuoteController.getQuote`'s `@PathVariable String ticker` now carries `@Pattern(regexp = "^[A-Za-z]{1,5}$")`, enforced via class-level `@Validated` (a method-level `@Validated` doesn't trigger Spring's method-validation proxy — had to be on the class). Case-insensitive because, unlike `TradeRequest`'s identical-looking constraint, this endpoint's input comes straight from user-typed text/URLs (navbar search, direct route nav), not an already-uppercased API response. Along the way found `ConstraintViolationException` (thrown by `@Validated` path-variable failures, distinct from `@Valid @RequestBody`'s `MethodArgumentNotValidException`) wasn't handled by `GlobalExceptionHandler` at all — confirmed via a failing test that it surfaced as an unhandled 500; added a handler so it returns a clean `400` + RFC 7807 body. New tests (invalid ticker → 400, lowercase ticker → 200) plus the full backend suite (52 tests) verified green.
- [x] Frontend error handling gaps — `stock-details.ts`: `fetchHoldingsData()` now has an `error` callback (previously none — a failed request was silently swallowed), and `fetchHoldingData()`/`fetchHoldingsData()` correctly distinguish "no position" (404, not an error) from real failures instead of rethrowing with no user-facing message. Three separate signals (`errorQuoteMessage`, `errorHoldingMessage`, `errorHoldingsMessage`) each surface next to exactly the data they govern in `stock-details.html`: a quote failure blocks the whole page (sibling to `notFound`/`quote`, same pattern as the rest of the app's inline-error convention); a holding failure blocks just the position-stats panel while leaving the quote/trade-form usable; a holdings-list failure only replaces the one derived value that depends on it (portfolio diversity → "Unavailable"), rather than hiding the whole panel. Also added `.stat-row-value.status-error` to `stock-details.css` — `.status-error` alone would've lost the cascade to `.stat-row-value`'s later color declaration. New tests (8, replacing the old create-only smoke test) cover all three error paths plus their normal-path counterparts; full frontend suite (38 tests) plus lint verified green.
- [x] Authorization — added a framework-level guard rather than relying on convention: `@EnableMethodSecurity` on `SecurityConfig` plus `@PreAuthorize("#userId == authentication.principal.user.id")` on all 5 `TradeService` methods (`buyStock`, `sellStock`, `getHolding`, `getHoldings`, `getTransactions`), binding each method's userId parameter to the authenticated principal — see [ADR 0035](./adr/0035-authorization-guard.md) (also records the scope call: default-deny method security was considered and rejected as disproportionate to a 3-controller app; per-entity ownership checks for a future non-user-scoped resource ID are noted as a gap to revisit, not solved here). `GlobalExceptionHandler` gained a dedicated `AccessDeniedException` handler (403 + RFC 7807 body) — first attempt caught `java.nio.file.AccessDeniedException` (wrong class entirely, not Spring Security's) and reused the `ConstraintViolationException` handler's mismatched method signature; both caught in review and fixed. Since no controller can currently trigger the deny path (every controller already derives userId from the principal, so there's no live IDOR to reproduce), new `TradeServiceAuthorizationTest` (6 tests) calls the real Spring-proxied service bean directly with a mismatched userId under a manually-set `SecurityContext` to prove the guard itself is wired and evaluated correctly; `GlobalExceptionHandlerTest` (1 test) covers the 403 mapping. Full backend suite (59 tests) plus spotless verified green.
- [x] Password-reset flow — locked-out/forgetful real users can now self-serve a reset; design in [ADR 0036](./adr/0036-password-reset-flow.md). New `password_reset_tokens` table (Flyway `V3`, `id`/`user_id`/`token_hash`/`expires_at`/`used_at`/`created_at`); tokens are a 32-byte `SecureRandom` value, only the SHA-256 hash persisted, 30-minute TTL, single-use. `EmailSender` interface + `LogEmailSender` (`@Profile("!prod")`, logs the link instead of sending it — prod has no working sender yet and `/auth/forgot-password` returns a generic `503`, identical for existing/non-existing emails so the enumeration-safe contract holds). `POST /auth/forgot-password` and `POST /auth/reset-password` added to `SecurityConfig`'s CSRF exemption and `permitAll()` list (pre-session, unauthenticated endpoints), plus a new `RateLimitGroup.FORGOT_PASSWORD` (client-IP keyed, 5/hour, mirrors `REGISTER`). A successful reset now also expires the user's other active sessions: `SecurityConfig` gained a `SessionRegistry`/`HttpSessionEventPublisher` (unlimited concurrent sessions, just tracked — no cap), and `PasswordResetService.resetPassword` walks `sessionRegistry.getAllPrincipals()`, matches by `User.getId()` (not `UserPrincipal.equals()`, which isn't overridden), and calls `expireNow()` on that user's sessions only. Frontend: `forgot-password`/`reset-password` standalone components under `guestGuard`, enumeration-safe inline confirmation, invalid/missing-token handling, no auto-redirect after reset (no session is created by this flow). Full backend suite (75 tests) verified green against real Postgres (Flyway `V3` validated); full frontend suite (53 tests, 15 files) green, lint clean. **Known gap, tracked not silent:** prod password reset isn't end-to-end usable until a real SES-backed `EmailSender` is built as part of AWS deployment sequencing.
- [x] Email verification at signup — split out from the item above per [ADR 0036](./adr/0036-password-reset-flow.md)'s scope note (password reset was built first); design in [ADR 0037](./adr/0037-email-verification-at-signup.md). No login gate — registration's existing auto-login/redirect is unchanged; verification only records a new nullable `User.emailVerifiedAt` (existing rows backfilled as verified in the same migration) and sends a link. New `email_verification_tokens` table (Flyway `V4`, same shape as `password_reset_tokens`). `EmailVerificationService.verifyEmail`/`resendVerification` reuse the existing `EmailSender`/`LogEmailSender` infra unchanged; `resendVerification` mirrors `resetRequest`'s enumeration-safe shape, skips issuing a token for already-verified users, and invalidates prior outstanding tokens before reissuing (`findByUserAndUsedAtIsNull`). `POST /auth/verify-email`/`resend-verification` added to `SecurityConfig`'s CSRF exemption and `permitAll()` list, plus a new `RateLimitGroup.EMAIL_VERIFICATION` (client-IP keyed, 5/hour, mirrors `FORGOT_PASSWORD`). Frontend: a reusable `NotificationService` (signal-backed, 15s auto-dismissing toast rendered once in `Layout` for every authenticated route — not verify-email-specific) shows a notice right before registration's existing `/dashboard` redirect; new `/verify-email` route (no `guestGuard`, since a freshly-registered user clicking the link is already logged in) auto-verifies on load and collapses expired/invalid into one failed state with an inline resend form, since the backend returns the same generic 400 for both and the UI doesn't fake a distinction the API can't back up. Full backend suite (92 tests) and frontend suite (77 tests) green, lint clean. Manually smoke-tested the full flow in browser. **Known gap, tracked not silent:** same as password reset — prod verification isn't end-to-end deliverable until a real SES-backed `EmailSender` exists.
