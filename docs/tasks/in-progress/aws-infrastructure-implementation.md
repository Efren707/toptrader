# AWS Deployment Infrastructure — Implementation Plan

> Tracks provisioning the AWS infrastructure itself — the last major body of work before TopTrader is actually live. The *shape* of this infra is already fully decided, not being redesigned here: [ADR 0005](../../adr/0005-aws-deployment-shape.md) (EC2+CloudFront/RDS/S3+CloudFront/Route 53), [ADR 0006](../../adr/0006-cicd-pipeline-design.md) (CI/CD), [ADR 0014](../../adr/0014-deployment-infrastructure.md) (network/IAM/budget detail), [ADR 0016](../../adr/0016-pipeline-stages.md)/[ADR 0017](../../adr/0017-merge-deploy-gates.md) (pipeline stages/gates), and consolidated in [docs/architecture/deployment-architecture.md](../../architecture/deployment-architecture.md). This doc breaks that decided shape into workable sections, sequenced by dependency, so it can be picked up one section at a time across multiple sessions — mirroring how [docs/tasks/completed/pre-deployment-checklist.md](../completed/pre-deployment-checklist.md) tracked hardening work. Each section is its own GitHub Issue under the [AWS Deployment Infrastructure milestone](https://github.com/Efren707/toptrader/milestone/14).

Two items already existed as GitHub Issues under the old Pre-Deployment Hardening milestone before this doc existed, and were reassigned onto this milestone since they're blocked on this same infra: **[#102](https://github.com/Efren707/toptrader/issues/102)** (CloudWatch log shipping + `StatusCheckFailed` alarm) picks up once section 4 (EC2) exists; **[#105](https://github.com/Efren707/toptrader/issues/105)** (automated rollback — last-known-good jar swap, [ADR 0039](../../adr/0039-rollback-strategy.md)) picks up once section 7 (CI/CD deploy wiring) exists. They're referenced inline below, not duplicated as new issues.

Working agreement applies as usual: one section at a time, check in before deciding anything not already settled by an ADR.

### 7. CI/CD deploy wiring

- [x] Frontend: OIDC-federated IAM role (repo/branch-scoped trust policy), `aws s3 sync` + CloudFront invalidation via GitHub Actions (ADR 0006) — GitHub OIDC identity provider added once at the account level (`token.actions.githubusercontent.com`, audience `sts.amazonaws.com`); IAM role `toptrader-frontend-deploy-role`, inline policy `toptrader-frontend-deploy-policy` scoped to `s3:ListBucket` on the `toptrader-frontend` bucket, `s3:PutObject`/`GetObject`/`DeleteObject` on its objects, and `cloudfront:CreateInvalidation` on distribution `E2QV9MPC8DTN65` only (**corrected 2026-08-09** — was originally scoped to `EBJQ07VSB22PM`, the *backend* distribution, due to the same ID mix-up noted in section 5; caught during section 8's cutover when the invalidation step would have had no effect on the real frontend distribution — see section 8); role ARN, bucket name, and distribution ID stored as GitHub repo secrets (`AWS_FRONTEND_DEPLOY_ROLE_ARN`, `FRONTEND_S3_BUCKET`, `FRONTEND_CLOUDFRONT_DISTRIBUTION_ID`) per ADR 0006. New `deploy-frontend` job in `.github/workflows/ci.yml`, gated on push-to-`main` and `frontend-ci` having actually succeeded (not skipped); downloads the `frontend-dist` artifact `frontend-ci` uploads rather than rebuilding, so what's deployed is exactly what passed lint/test/build. First live run failed with `Not authorized to perform sts:AssumeRoleWithWebIdentity` — the trust policy's `sub` condition assumed the classic `repo:OWNER/REPO:ref:REF` format, but this account's actual OIDC tokens include immutable numeric IDs: `repo:Efren707@53492872/toptrader@1303366426:ref:refs/heads/main`. Root-caused by adding a temporary workflow step that fetched and base64-decoded the real token to inspect its claims directly (removed once fixed); trust policy corrected to the real value.
- [x] Backend: SSH-key GitHub secret, SCP the built jar + `systemctl restart` (ADR 0006) — dedicated low-privilege `deploy` Linux user on EC2 (not `ec2-user`), keyed with its own ed25519 pair generated locally (private key never touches the server); `deploy` is a member of the `toptrader` group, and both `/opt/toptrader` itself and its contents are group-writable; has exactly one NOPASSWD sudoers entry (`/usr/bin/systemctl restart toptrader.service`, no wildcard) — verified live that `deploy` can restart the service but is correctly denied `systemctl status`/`journalctl` (no matching sudoers rule). Private key stored as GitHub secret `EC2_DEPLOY_SSH_KEY`. `backend-ci` copies the repackaged jar to a fixed `app.jar` name and uploads it as a build artifact. First live run failed: `appleboy/scp-action`'s tar-based extraction couldn't `chmod`/`utime` the existing `app.jar` it doesn't own (`toptrader:toptrader`) even with group-write permission on that file — Unix only lets the owner (or root) change a file's mode/mtime. Fixed by staging the upload as `app.jar.new` (always freshly created, always owned by `deploy`) and having the restart step `mv` it over `app.jar` — a same-directory rename only needs directory write permission, not ownership of the file being replaced.
- [x] ~~SSM Parameter Store secrets pulled at deploy time~~ — superseded by ADR 0041 (section 4): the `toptrader.service` unit's `ExecStartPre` fetches `/toptrader/prod/*` on every start, so the deploy script needs no SSM logic at all
- [x] Post-deploy smoke test: curl `/actuator/health` with retry/backoff after restart, fail the deploy job if unhealthy (ADR 0017) — scoped into this section rather than deferred to #105, since #105's rollback needs this signal to trigger off. Implemented inline in `deploy-backend`'s `appleboy/ssh-action` step: restart, then up to 10 attempts 3s apart (~30s window) curling `/actuator/health` for `"status":"UP"`, failing the step (and job) if it never comes up healthy. Window sized off a real observed startup of ~12s (Flyway validate + Hibernate + Tomcat) — roughly 2x margin.
- [x] Wire the deploy stage into the existing lint→test→build pipeline, gated on merge to `main` only (ADR 0016/0017) — satisfied by construction: both `deploy-frontend` and `deploy-backend` live in the same `.github/workflows/ci.yml`, each gated on `github.ref == 'refs/heads/main' && (github.event_name == 'push' || github.event_name == 'workflow_dispatch')` plus their respective CI job actually succeeding (not skipped). A `workflow_dispatch` trigger was added alongside the automatic push-to-`main` one, so the full pipeline (deploy jobs included) can be manually re-run from the Actions tab for verification without needing a throwaway source commit each time — doesn't change ADR 0017's automatic-on-merge deploy trigger, just adds a manual path alongside it.

**End-to-end verification**: both bugs above only surfaced on a real deploy (a syntactically-valid workflow isn't the same as a working one) — first live run after merging the initial implementation failed both jobs for the reasons described above; after fixing both and manually re-dispatching the workflow on `main`, `deploy-frontend` and `deploy-backend` both completed successfully.

### 8. Cutover & smoke test

- [x] Route 53 DNS cutover to the live CloudFront distributions — alias A records created in the `toptrader.dev` hosted zone: `app.toptrader.dev` → `toptrader-frontend` distribution, `api.toptrader.dev` → `toptrader-backend` distribution (AAAA/IPv6 records skipped for now, deferred). Verification (`nslookup` + `curl`) surfaced two real bugs, both pre-existing since sections 5/7 and only now surfaced because this was the first real traffic through them:
  1. **CloudFront distribution IDs were swapped throughout this doc from the start** — `EBJQ07VSB22PM` is actually `toptrader-backend` (EC2 origin) and `E2QV9MPC8DTN65` is actually `toptrader-frontend` (S3 origin), the reverse of what sections 5-7 originally recorded. Doc corrected in place at each occurrence (sections 5, 6, 7) rather than kept as a running note.
  2. **Backend distribution's origin domain was stale** — `toptrader-backend`'s (`EBJQ07VSB22PM`) origin was pointing at `ec2-3-16-138-189.us-east-2.compute.amazonaws.com`, not the instance's actual Elastic IP DNS name `ec2-18-226-207-9.us-east-2.compute.amazonaws.com` (confirmed current/correct via the EC2 console). Root cause: wrong dropdown selection when the origin was first configured in section 5 — never surfaced until now because no real traffic hit it before this cutover. Fixed by editing the origin domain to the correct EIP DNS name.
  3. **Consequence of bug 1**: `toptrader-frontend-deploy-policy`'s `cloudfront:CreateInvalidation` permission (section 7) and the `FRONTEND_CLOUDFRONT_DISTRIBUTION_ID` GitHub secret were both scoped to `EBJQ07VSB22PM` — the wrong (backend) distribution — since the pipeline was built. Every frontend deploy's cache-invalidation step had no effect on the real frontend distribution. Fixed by updating the IAM policy's `Resource` ARN and the GitHub secret value to `E2QV9MPC8DTN65`, then confirmed via a manual `workflow_dispatch` run of the full CI/CD pipeline — `deploy-frontend`'s "Invalidate CloudFront cache" step and `deploy-backend`'s post-deploy smoke test both passed.
  
  After both fixes: `https://app.toptrader.dev` → `200`, `https://api.toptrader.dev/actuator/health` → `200 {"status":"UP"}`.
- [x] End-to-end smoke test against the real domain (register, login, quote lookup, buy/sell, portfolio/transactions/performance views) — register/login/quote lookup worked immediately; logout and buy both failed with `403 Forbidden`, surfacing a real cross-subdomain CSRF bug (pre-existing since `SecurityConfig`'s CSRF setup was written, only surfaced now that `app.`/`api.` are real separate origins for the first time):
  1. **CSRF cookie not readable across subdomains** — `.spa()`'s default `CookieCsrfTokenRepository` scopes the `XSRF-TOKEN` cookie to the responding host (`api.toptrader.dev`) with no explicit `Domain`, so `document.cookie` on `app.toptrader.dev` couldn't read it and Angular had no token to echo back as `X-XSRF-TOKEN` — every CSRF-protected POST (logout, buy, sell) was rejected. Fixed by adding a `toptrader.csrf-cookie-domain` property (new `/toptrader/prod/csrf-cookie-domain` SSM parameter, exported by `fetch-secrets.sh`) applied via `CookieCsrfTokenRepository.setCookieCustomizer`. New tests in `SecurityConfigTest`/`SecurityConfigCsrfCookieDomainTest` exercise the real cookie/header round-trip rather than the `SecurityMockMvcRequestPostProcessors.csrf()` test shortcut that was masking this. [PR #131](https://github.com/Efren707/toptrader/pull/131).
  2. **First deploy of fix #1 crashed the live app** — the SSM parameter's initial value (`.toptrader.dev`, leading dot) is invalid per RFC 6265; Tomcat's `Rfc6265CookieProcessor` rejects it and threw on every request (since `CsrfCookieFilter` forces the cookie to resolve unconditionally), taking `/actuator/health` itself down. `MockMvc`'s test dispatcher doesn't route through Tomcat's real cookie validation, so this format issue wasn't caught locally, only after deploying to the real EC2/Tomcat stack. Fixed by dropping the leading dot (`toptrader.dev`) in both the SSM parameter and the test. [PR #132](https://github.com/Efren707/toptrader/pull/132).
  
  After both fixes and a hard browser reload (stale pre-fix cookies were still cached): full checklist confirmed working live — register, login, logout, quote lookup, buy, sell, holdings/portfolio, transactions, performance view.
- [x] Build a real SES-backed `EmailSender` — password reset / email verification are implemented but not end-to-end usable without it (ADR 0036/0037). Closes the prod gap both ADRs flagged: `SesEmailSender` (`@Profile("prod")`) implements `EmailSender` using AWS SDK v2's `ses` module (ADR 0044). SES domain identity verified for `toptrader.dev` (Easy DKIM, records auto-published to the existing Route 53 zone), production access requested and approved (out of the sandbox), new scoped `toptrader-ses-send-policy` (`ses:SendEmail`/`SendRawEmail` on just the one identity ARN) attached to the existing `toptrader-ec2-role`, new `/toptrader/prod/mail-from-address` SSM parameter exported by `fetch-secrets.sh` as `TOPTRADER_MAIL_FROM_ADDRESS`. Send failures are caught and logged (`WARN`, recipient + cause), not rethrown, keeping `resetRequest()`'s enumeration-safe response behavior intact on a transient SES failure. Verified end-to-end with a manual pre-merge deploy (built jar SCP'd directly to EC2, service restarted, real `POST /auth/forgot-password` against a real registered email) — password-reset email received in inbox with the actual reset link, confirming DKIM/IAM/SSM wiring all work together, ahead of the normal PR/CI-CD deploy path.
- [x] Check the frontend's blank-page-on-network-error behavior in `checkSession()`'s app initializer against the real API origin (network error / wrong or unreachable API origin currently renders a blank page instead of falling back to a logged-out view) — folded into the smoke test above: direct navigation to `app.toptrader.dev` and `app.toptrader.dev/login` both loaded correctly now that `api.toptrader.dev` is reachable; no blank page observed
